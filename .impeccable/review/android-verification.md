# Android Adaptation Verification

Historical adaptation record. The current UI, APK and latest validation are
documented in [android-polish-verification.md](android-polish-verification.md).

Date: 2026-11-08 (Asia/Shanghai). Project: NearLink 0.3.0+15.

## Scope

Android 8.0 / API 26 and later. The existing Windows product and running Windows
application were not installed over, restarted or stopped during this adaptation.
The existing blue, cool-white and mint identity, brand assets, shared LAN protocol,
transfer implementation, messages, remarks and groups remain the product reference.
DESIGN.md and .impeccable/design.json were preserved; Android-specific behavior and
the quality bar are documented in .impeccable/surfaces/android.md.

## Native Validation

LDPlayer 14.0.34.1 runs Android 14 with an Android display override of 1080x1920
at 420 dpi. The APK installed successfully and cold-launched after each update.
The final app-process log is `android-native-logcat.txt`; it contains no Flutter
unhandled exception, MissingPluginException, AndroidRuntime fatal exception or
unsupported `reusePort` error. Vendor graphics diagnostics remain in the log.

Verified on the emulator:

- Five navigation pages, Chinese text and icons; chat navigation and Android Back.
- Native notification permission request and grant on Android 14.
- Opt-in connected-device foreground service, persistent notification, and its
  stop action. `dumpsys activity services` confirmed the foreground service while
  enabled and no active service after stopping. It was left disabled afterward.
- Background messages aggregated as two unread messages. Tapping the native
  notification opened the matching conversation.
- Background file notification with accept/reject actions. Accept completed a
  three-file batch and produced a native completion notification.
- System document picker selected three files. ACTION_CREATE_DOCUMENT exported
  three received files to Download. The exported empty file, 1,536-byte text and
  8 MiB binary matched the source SHA-256 values.
- Hardware-keyboard input retained a newline and the multi-line reply was delivered.
  A generated ACTION_SEND text intent also required explicit recipient selection
  and sending, then arrived at the isolated test peer.
- Final bidirectional three-file transfer and message reply passed with exit code
  zero. Evidence: `build/android-verification/peer-eebaedc2/result.json` and its
  `state/logs/nearlink.jsonl`. All returned SHA-256 values match the fixtures.

Windows-to-Android used an ephemeral local ADB forward. Android-to-Windows file
return used an explicit host LAN address (`192.168.3.60:55979`) through emulator
NAT. The final peer log retained its manually selected forwarded endpoint even
after the return offer; no other peer was probed in that final run. The ADB
forward was removed after testing. These checks do not validate automatic UDP
discovery across the emulator NAT or between physical devices.

No physical phone is connected. LDPlayer's bundled Pinyin IME reported itself
shown but did not render a normal phone keyboard. Multi-line hardware input was
verified; a real on-screen IME, keyboard resize behavior, gesture navigation,
long background transfers and OEM battery policies still require phone testing.

Background reception is an opt-in connected-device foreground service with a
persistent notification and stop action, not an unconditional delivery guarantee.
Android and OEM process/battery restrictions still apply. Received files initially
live in app-private storage; uninstalling or clearing app data deletes them unless
the user exports them first. This behavior is disclosed in Settings and ANDROID.md.

The installable preview uses the local development signing certificate. A persistent
private release key and controlled release process are still required for a formal
distribution and reliable updates across build machines.

The user completed the installer click after desktop automation input did not

launched and ADB connected at `127.0.0.1:5555`. No host reboot or Windows security

Native testing exposed and fixed two network defects: Android cannot use Dart's
`reusePort` option, and manual connection routes must retain their entered port
and survive inbound handshakes. A regression test covers a mapped endpoint whose
advertised internal port differs and an inbound hello before sending a message.
The full shared service, desktop and Android test suite passed after these fixes.

Before the route fix, one generated test message and a three-file offer reached
the existing local Windows NearLink endpoint. The offer expired/rejected without
transferring file contents; its sender history is in `peer-ff45a5da`. Existing
Windows data was not edited to remove these synthetic records. Subsequent native
checks used the isolated test peer and the correct forwarded Android endpoint.

`tool/verify_android_peer.dart` was added for isolated interoperability checks.
Its analyzer passed. Its initial `--self-test` passed with two local service
instances. The final native run also passed against LDPlayer, as recorded above.
Actual emulator captures use the `android-native-*.png` prefix; the overview is
`android-native-overview.png`. These are separate from the widget-test previews.
